CSVAT Architecture Q&A

1. Populate State/District/Tehsil Dropdown:
The frontend makes an API call to the CoRE Stack "get_active_locations" endpoint. This returns a nested JSON hierarchy (State -> District -> Tehsil -> Block). The React UI parses this JSON to populate the cascading dropdowns automatically.

2. Raster Download vs Pre-computed Data:
We do NOT download the underlying rasters to do custom computations on our backend. Instead, we query the CoRE Stack APIs (like "get_tehsil_data") which return the *already pre-computed* statistics (like cropping intensity and water seasonality) for those exact boundaries in a lightweight JSON payload.

3. GEE Fallback vs CoRE Stack Assets:
You are correct; GEE (using sources like MODIS) provides coarse 250m-500m resolution data, which lacks the granular fidelity needed to replicate CoRE Stack's proprietary LULC classifications (like delineating single/double crop fields). Therefore, we rely strictly on CoRE Stack APIs for all tier-1 precision agricultural data. The GEE pipeline serves purely as a fallback mechanism to run baseline planetary computations (like rough NDVI metrics) for geographies where CoRE Stack pre-computed granular data does not yet exist.

4. Automated Data Narrative:
The narrative is built using string templating. Once the data for a boundary is fetched (i.e., Total Area = 500ha, Net Sown Area = 45%, etc.), those variables are injected into pre-written text templates in the frontend code. Simple logic gates (IF trend > 0 THEN "increasing" ELSE "decreasing") make the text read dynamically.

5. Server-side vs WASM (Client-side) Compute:
Exactly right. 
- Server-Side: Web browser -> FastAPI Backend -> Fetches from CoRE Stack/GEE -> Aggregates -> Sends final data back to browser.
- WASM (Client-Side): Web browser loads Python (via Pyodide) -> Browser makes direct HTTP requests to CoRE Stack APIs -> Runs pandas/geopandas entirely inside the user's local browser -> Outputs report (zero load on our backend server).
